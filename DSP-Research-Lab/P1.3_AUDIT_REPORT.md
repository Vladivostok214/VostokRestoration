## 1. RESUMEN EJECUTIVO

De los 6 cuellos de botella identificados en `INFORME_TECNICO_OPTIMIZACION.md`, **5 siguen presentes sin mitigación**. El único cerrado parcialmente es el de modularización (`lib.rs`), que mejoró en legibilidad mediante P1.1 pero conserva toda la lógica Tauri de comandos.

El cuello de mayor impacto medible en **RAM + latencia percibida** es el clone de buffer de audio en playback. El de mayor impacto en **CPU + latencia de análisis** es la STFT doble estéreo. El cuello de mayor impacto en **IPC** es `reparar_glitches_seleccionados` retornando el espectrograma completo.

## 2. ESTADO DE LOS CUELLOS DE BOTELLA

### CB-1 — Re-cálculo STFT por canal en análisis estéreo

**Estado: CONFIRMADO — Sin mitigación**

**Evidencia en código:**

```
// detectors.rs L1117–L1131
let mut all_events = (0..n_channels)
    .into_par_iter()
    .map(|c| {
        let chan_samples: Vec<f32> = audio.samples.iter().skip(c).step_by(n_channels).cloned().collect();
        let chan_audio = AudioBuffer { samples: chan_samples, ... };
        // Compute a channel-specific STFT for the detector features
        let chan_stft = compute_stft(&chan_audio.samples, 4096, 1024, "blackman-harris").unwrap();
        ejecutar_analisis_dsp_mono(&chan_audio, &chan_stft, params, c as u16)
    })
```

**Análisis:**

- `ejecutar_analisis_avanzado` en `lib.rs` llama a `ejecutar_analisis_dsp(audio_buf, stft_res, &params)` con el `stft_res` ya cargado en `AppState`.
- Sin embargo, `ejecutar_analisis_dsp` en `detectors.rs` **ignora ese `stft_res` global** y llama `compute_stft` de nuevo por canal en estéreo.
- La STFT global ya calculada en `AppState` (4096/1024 Blackman-Harris) es descartada y recomputada dos veces (L+R) con los mismos parámetros.
- El lock de `audio_lock` y `stft_lock` se mantiene **durante todo el análisis DSP** (lib.rs L920–934), bloqueando otros comandos Tauri mientras dura la recomputación.

**Impacto estimado** (audio estéreo 48kHz, 3 min, ~8.6M samples):

| Métrica | Estimación |
|---------|-----------|
| Allocations extra | 2× `Vec<f32>` de ~4.3M elementos = ~33 MB extra transitorios |
| CPU extra | 2× STFT completa = ~200–500ms adicionales vs mono en hardware mid-range |
| Bloqueo Tauri | Playback/export bloqueados durante todo el análisis |
| Origen | `detectors.rs:1130` — `compute_stft()` ignorando la STFT global |

**¿Mitigado por P0/P0.2/P1.1?** No. P1.1 movió el código a un módulo separado, pero la lógica es idéntica.

### CB-2 — Copias y de-interleave de buffers multicanal

**Estado: CONFIRMADO — Sin mitigación**

**Evidencia en código:**

```
// detectors.rs L1121
let chan_samples: Vec<f32> = audio.samples.iter().skip(c).step_by(n_channels).cloned().collect();

// stft.rs L91
let chan_samples: Vec<f32> = samples.iter().skip(c).step_by(n_channels).cloned().collect();

// lib.rs L319 (reparación quirúrgica, modo click/pop)
let chan_samples: Vec<f32> = audio_buf.samples.iter().skip(c as usize).step_by(n_channels).cloned().collect();

// lib.rs L379 (reparación quirúrgica, modo distortion)
let mut chan_samples: Vec<f32> = audio_buf.samples.iter().skip(c as usize).step_by(n_channels).cloned().collect();

// lib.rs L411 (history distortion)
let old_chan_samples: Vec<f32> = audio_buf.samples.iter().skip(c as usize).step_by(n_channels).cloned().collect();
```

**Análisis:**

- El patrón `.iter().skip(c).step_by(n).cloned().collect()` aparece **en al menos 5 lugares distintos**.
- Cada llamada aloca un Vec completo de N/channels elementos. Para audio estéreo de 3 min a 48kHz: ~4.3M f32 = ~17.2 MB por llamada.
- `compute_stft_multichannel` (stft.rs L88–112) hace N allocations de Vec por canal + 1 Vec de combinación `combined_matrix`. Total: 3× buffer completo para estéreo.
- `update_stft_range_multichannel` (stft.rs L218–252) aloca `chan_slice` por canal en cada actualización parcial.
- El rango parcial en `update_stft_range_multichannel` es una mejora real: el rango afectado puede ser de cientos a miles de samples, no millones. **Este es el único punto donde las allocations están acotadas en tamaño.**

**Impacto estimado:**

| Métrica | Estimación |
|---------|-----------|
| RAM transitoria extra (análisis estéreo) | ~34–51 MB por ejecución de análisis |
| RAM transitoria extra (reparación con modo click) | ~17 MB por canal por operación |
| Presión GC/allocator | Alta: objetos grandes de vida corta sin reutilización |
| Latencia visible | +50–200ms en análisis completo de archivos largos |

**¿Mitigado por P0/P0.2/P1.1?** No. P1.1 consolidó el código, pero el patrón de de-interleave es el mismo.

### CB-3 — Playback clonando buffers completos

**Estado: CONFIRMADO — CUELLO MÁS CRÍTICO EN RAM**

**Evidencia en código:**

```rust
// lib.rs L793–798
let (samples, channels, sample_rate) = {
    let audio_lock = app.audio.lock().unwrap();
    match &*audio_lock {
        Some(buf) => (buf.samples.clone(), buf.channels, buf.sample_rate),
        //                  ^^^^^^^^^^^^ CLONE COMPLETO
        None => return Err("..."),
    }
};
// ... lock liberado aquí (bien hecho)

// lib.rs L858–862 — el clone se consume en SamplesBuffer::new
let source_buffer = rodio::buffer::SamplesBuffer::new(
    channels,
    sample_rate,
    samples,  // Vec<f32> completo transferido a rodio
);
```

**Análisis:**

- Cada `toggle_playback` con seek (o primera reproducción) clona **todo el buffer PCM de audio**.
- Para audio estéreo de 3 min a 48kHz/32bit: ~50 MB de clone por operación de seek.
- `rodio::SamplesBuffer` toma ownership del `Vec<f32>`, por lo que el clone es inevitable con la API actual.
- El lock de audio se libera **antes** de la llamada a `iniciar_reproduccion_interna` (lib.rs L802) — esto es correcto y fue mejorado en P0.
- El skip_duration implementa seek por descarte de samples: itera todo el buffer desde el inicio hasta `start_time`, sin acceso aleatorio real.

**Impacto estimado:**

| Métrica | Estimación |
|---------|-----------|
| RAM extra por seek/play | = tamaño del audio en RAM (puede ser 20–200 MB) |
| Latencia de seek | Proporcional a la duración del archivo; sin O(1) seek |
| Seeks frecuentes | Cada uno aloca + libera N MB |
| Riesgo OOM | Moderado en archivos >30 min a alta resolución |

**¿Mitigado por P0/P0.2/P1.1?** Parcialmente en P0: el lock se libera antes del clone, eliminando el deadlock. Pero el clone completo persiste.

### CB-4 — `get_paged_spectrogram` procesando matrices completas

**Estado: CONFIRMADO — Sin mitigación**

**Evidencia en código:**

```rust
// stft.rs L117–175
pub fn get_paged_spectrogram(stft: &StftResult, config: &ViewportConfig) -> StftResult {
    // ...
    if visible_frames_len <= config.max_texture_width {
        // Caso sin downsampling: copia slice completo
        let mut sub_matrix = vec![0.0; visible_frames_len * num_bins];
        sub_matrix.copy_from_slice(&stft.matrix[src_start_offset..src_end_offset]);
        // ...
    }
    
    // Caso con downsampling: triple loop SECUENCIAL
    for dest_f in 0..target_width {
        for k in 0..num_bins {
            for src_f in src_start_f..src_end_f {  // ← loop interno variable
                let val = stft.matrix[src_f * num_bins + k];
                sum_sq += val * val;
            }
            downsampled_matrix[dest_offset + k] = (sum_sq / count).sqrt();
        }
    }
}
```

**Análisis:**

- Función llamada en: `obtener_espectrograma_visible`, `obtener_espectrograma_dinamico` (fallback), `reparar_glitches_seleccionados`, `deshacer_accion`, `rehacer_accion`.
- El triple loop de downsampling es **O(target_width × num_bins × step)** donde `step = total_frames / target_width`. Con 4096/1024: num_frames típico ~2700 frames para 3 min, num_bins = 2048. Step = 2700/2048 ≈ 1.3. El loop interno es casi degenerado para la escala actual.
- **El problema real:** la función siempre aloca un `StftResult` nuevo con hasta 2048 × 2048 f32 = 16 MB de datos, sin importar qué tan pequeña sea la región visible.
- No está paralelizada con Rayon.
- Llamada con `max_texture_width: 2048` y `start_frame: 0, end_frame: stft_res.num_frames` en reparación/undo/redo = **siempre procesa la matriz entera**.

**Impacto estimado:**

| Métrica | Estimación |
|---------|-----------|
| Allocación por llamada | 2048 × 2048 × 4 bytes = ~16 MB |
| IPC payload | 16 bytes header + 2048×2048 bytes u8 = ~4 MB de datos serializados |
| Latencia IPC | 50–150ms para transferir 4 MB via Tauri IPC JSON/binary |
| Frecuencia | Cada reparación, undo, redo = mínimo 1 llamada |

**¿Mitigado por P0/P0.2/P1.1?** No. `audio_version` (P0.2) evita que el frontend consuma versiones obsoletas, pero no reduce el tamaño del payload.

### CB-5 — Reparación devolviendo espectrograma completo tras cambios locales

**Estado: CONFIRMADO — Cuello de IPC más grave**

**Evidencia en código:**

```rust
// lib.rs L546–553 (reparar_glitches_seleccionados)
// Generar espectrograma completo
let full_viewport = ViewportConfig {
    start_frame: 0,
    end_frame: stft_res.num_frames,  // ← SIEMPRE TODO
    max_texture_width: 2048,
};
let paged_stft = dsp::get_paged_spectrogram(stft_res, &full_viewport);
let spectrogram = dsp::stft_to_binary(&paged_stft, current_version);

// lib.rs L656–661 (deshacer_accion) — IDÉNTICO
// lib.rs L748–753 (rehacer_accion) — IDÉNTICO
```

**Análisis:**

- La actualización STFT **ya es parcial y eficiente** gracias a `update_stft_range_multichannel` (correctamente implementado en stft.rs).
- Sin embargo, el payload IPC siempre envía el espectrograma **completo** (2048 frames × 2048 bins = ~4 MB serializado).
- Una reparación de un click de 10 samples (que afecta ~5 frames STFT) igualmente serializa y transmite los ~4 MB completos.
- El frontend (`SpectrogramGL.jsx`) recarga la textura WebGL completa en cada respuesta.
- Este cuello existe en **3 comandos**: reparar, deshacer, rehacer.

**Impacto estimado:**

| Métrica | Estimación |
|---------|-----------|
| Payload IPC innecesario | ~3.95 MB de datos por reparación de click (99.8% datos sin cambio) |
| Latencia de reparación percibida | 100–300ms solo en IPC, más tiempo de carga de textura WebGL |
| Escalabilidad | Lineal con duración del audio, no con tamaño de la reparación |

**¿Mitigado por P0/P0.2/P1.1?** Parcialmente en P1.1: `update_stft_range_multichannel` ya actualiza solo el rango afectado. Pero falta la mitad del trabajo: el IPC sigue enviando todo. P0.2 provee `audio_version` que podría ser el mecanismo de sincronización para actualizaciones parciales, pero no se usa para eso aún.

### CB-6 — Concentración de lógica en `lib.rs`

**Estado: PARCIALMENTE MITIGADO por P1.1**

**Evidencia en código:**

- `dsp.rs` es ahora una fachada de re-exportación pura de 13 líneas. ✅
- `lib.rs` mide **977 líneas** (era ~946 en INFORME_TECNICO). El tamaño no se redujo significativamente.
- `lib.rs` contiene: 10 comandos Tauri + 2 helpers + 3 structs de respuesta + lógica de undo/redo de hasta 120 líneas por comando.
- La lógica DSP pesada (cálculos, loops de reparación) se delegó correctamente a `vostok_dsp/`.
- Lo que permanece en `lib.rs` es: orquestación de locks, serialización IPC, lógica de modo quirúrgico (líneas 295–488, ~193 líneas para un solo path de reparación).

**Análisis:**

- El modo quirúrgico (`is_selection = true`) tiene 3 sub-caminos (transitorios/distorsión/continuos) embebidos directamente en `reparar_glitches_seleccionados`. Es el bloque más largo con ~350 líneas.
- `aplicar_reparacion_quirurgica` es un comando redundante (comentado como tal en INFORME_TECNICO, línea 68). Sigue existiendo.
- `RepairResponse` struct existe y nunca se usa (L252–255).

**Impacto:**

| Métrica | Estimación |
|---------|-----------|
| Riesgo de regresión | Alto por tamaño y lógica anidada |
| Costo cognitivo | Medio-alto; el modo quirúrgico es difícil de rastrear |
| CPU/RAM/IPC | Cero impacto directo |

**¿Mitigado por P0/P0.2/P1.1?** Solo el aspecto de DSP puro. La orquestación sigue en `lib.rs`.

## 3. HALLAZGOS ADICIONALES (FUERA DEL INFORME ORIGINAL)

### F-A — `stft_to_binary` no paralelizado

```rust
// io.rs L133–137 — Loop escalar
for &mag in &stft.matrix {
    let db = 20.0 * mag.max(1e-6).log10();
    let normalized = (db - noise_floor_db) / -noise_floor_db;
    buf.push((normalized.clamp(0.0, 1.0) * 255.0) as u8);
}
```

- El INFORME_TECNICO ya lo identificaba como oportunidad de paralelización.
- Para 2048×2048 = ~4.2M operaciones de `log10` por llamada. Con Rayon por chunks: potencial 4–8× speedup en hardware multicore.
- El `log10` no tiene SIMD nativo en Rust estable sin libm; candidato a LUT de 256 entradas.

### F-B — Planes FFT recreados en cada `update_stft_range_multichannel`

```rust
// stft.rs L204–205
let mut planner = RealFftPlanner::<f32>::new();
let r2c = planner.plan_fft_forward(fft_size);
```

- Se crea un nuevo `RealFftPlanner` en cada actualización parcial de STFT.
- `RealFftPlanner` internamente crea y cachea planes via `Arc`, pero la instancia del `planner` en sí es nueva cada vez.
- Para reparaciones múltiples en sesión, se podrían reutilizar los planes.

### F-C — `ejecutar_analisis_avanzado` mantiene 2 locks durante todo el DSP

```rust
// lib.rs L920–931
let audio_lock = app.audio.lock().unwrap();
let stft_lock = app.stft.lock().unwrap();

if let (Some(ref audio_buf), Some(ref stft_res)) = (&*audio_lock, &*stft_lock) {
    let mut glitches = dsp::ejecutar_analisis_dsp(audio_buf, stft_res, &params);
    // ... audio_lock y stft_lock se liberan aquí al salir del bloque
```

- El análisis DSP completo (que puede durar >1s en archivos largos) se ejecuta con `audio_lock` y `stft_lock` activos.
- Cualquier comando que necesite `audio` o `stft` (playback, export, espectrograma) queda bloqueado durante el análisis.
- Corrección P0 identificó esto pero no fue implementada (el comentario en INFORME_TECNICO era prospectivo).

### F-D — `unwrap()` sobre mutex/FFT en paths críticos

- `detectors.rs L1130`: `compute_stft(...).unwrap()` sin propagación de error. Puede panicar ante audio corrupto o FFT con tamaño 0.
- `stft.rs L64`: `r2c.process(...).unwrap()` en el inner loop paralelo de Rayon. Un panic en Rayon puede ser no-determinístico.
- `lib.rs L539, 647, 739`: `stft_lock.as_ref().unwrap()` tras bloque de garantía implícita. Seguro en flujo normal, frágil si se refactoriza.

### F-E — `RepairResponse` struct huérfana

```rust
// lib.rs L252–255
pub struct RepairResponse {
    pub spectrogram: Vec<u8>,
    pub waveform_envelope: Vec<f32>,
}
```

- Definida pero nunca instanciada ni retornada. Se usa `UndoRedoResponse` en su lugar.
- Deuda técnica nivel P2.

### F-F — `println!` en paths de reparación en producción

- 5 llamadas a `println!` en `lib.rs` sin debug guard (líneas 301, 336, 445, 558, 829).
- En producción (release build) generan I/O de disco/consola en el hilo Tauri durante reparación.

## 6. RANKING ACTUALIZADO DE PRIORIDAD P1.3

> Criterio de ranking: Impacto / (Riesgo de Regresión × Complejidad de Implementación)

### 🥇 P1.3-A — Playback sin clone (CB-3)
- **Impacto:** Elimina hasta N MB de RAM por seek. Directamente visible para usuario.
- **Complejidad:** Media. Requiere `Arc<[f32]>` + fuente custom rodio.
- **Riesgo de regresión:** Bajo. Aislado en `toggle_playback` / `iniciar_reproduccion_interna`.
- **Dependencias:** Ninguna.

### 🥈 P1.3-B — Locks cortos en análisis avanzado (F-C)
- **Impacto:** Elimina bloqueo de playback/export durante análisis. UX inmediata.
- **Complejidad:** Baja. Clone controlado de `AudioBuffer` + `Arc<StftResult>` antes de soltar lock.
- **Riesgo de regresión:** Bajo. Solo afecta `ejecutar_analisis_avanzado`.
- **Dependencias:** Ninguna.

### 🥉 P1.3-C — STFT estéreo sin re-cálculo (CB-1)
- **Impacto:** Elimina STFT doble en cada análisis estéreo. Reducción de ~50% de CPU+RAM en análisis.
- **Complejidad:** Media-Alta. Requiere cambiar firma de `ejecutar_analisis_dsp` para aceptar STFT por canal, o cachear en `AppState`.
- **Riesgo de regresión:** Medio. Afecta el flujo central de análisis.
- **Dependencias:** Ninguna técnica, pero pre-requisito conceptual de CB-2.

### 4️⃣ P1.3-D — IPC parcial post-reparación (CB-5 + CB-4)
- **Impacto:** Reducción de payload IPC de ~4 MB a ~KB para reparaciones locales.
- **Complejidad:** Alta. Requiere: (a) `get_paged_spectrogram` con rango dirty, (b) nuevo tipo de mensaje IPC de parche de textura, (c) actualización parcial de textura en SpectrogramGL.jsx (WebGL `texSubImage2D`).
- **Riesgo de regresión:** Alto. Toca frontend WebGL y protocolo IPC.
- **Dependencias:** CB-4 y F-A son pre-requisitos.

### 5️⃣ P1.3-E — `stft_to_binary` paralelo (F-A)
- **Impacto:** Speedup 4–8× en serialización para textura completa.
- **Complejidad:** Baja. Agregar `par_iter()` de Rayon + considerar LUT de log10.
- **Riesgo de regresión:** Muy bajo. Función pura sin estado.
- **Dependencias:** Ninguna. Puede implementarse de forma independiente.

### 6️⃣ P1.3-F — De-interleave sin allocations completas (CB-2)
- **Impacto:** Reducción de RAM transitoria en análisis y reparación.
- **Complejidad:** Alta. Requiere iteradores especializados o buffers persistentes en AppState.
- **Riesgo de regresión:** Medio. Afecta múltiples paths.
- **Dependencias:** Mejor atacar después de CB-1 (que elimina el de-interleave del análisis).

## 8. INVARIANTES A PRESERVAR

> Estos contratos no deben romperse en ningún sprint de P1.3.

1. **IPC header:** `[frames:u32][bins:u32][audio_version:u64]` = 16 bytes exactos al inicio de cualquier payload de espectrograma.
2. **audio_version:** debe incrementarse en carga, reparación, undo y redo. Nunca retroceder.
3. **Alineación temporal:** la versión del `audio_version` embebida en el payload binario debe corresponder a la versión en el momento de serialización, no en el momento de la llamada.
4. **QA obligatorio:** antes de cerrar cualquier sprint, ejecutar el checklist completo: carga, playback, zoom, selección, análisis, reparación, undo, redo, export WAV.
