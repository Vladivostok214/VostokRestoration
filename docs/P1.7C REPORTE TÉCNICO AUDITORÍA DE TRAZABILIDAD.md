REPORTE TÉCNICO: AUDITORÍA DE TRAZABILIDAD (P1.7C)

  ### 1. Localización del Origen Exacto

  El origen se encuentra en  src-tauri/src/vostok_dsp/detectors.rs  (línea ~620). Cuando  detectar_clipping()  encuentra un candidato válido,
  genera el siguiente struct:

    events.push(GlitchEvent {
        sample_index: i,
        time_secs: i as f64 / sample_rate as f64,
        amplitude_delta: val,
        direction: if samples[i] > 0.0 { 1 } else { -1 },
        event_type: GlitchType::Distortion, // <--- AQUÍ SE ASIGNA
        repaired: false,
        frequency: None,
        channel: 0,
        duration_samples: Some(count),
    });

  ¿Qué  GlitchType  asigna? Asigna  GlitchType::Distortion .

  ### 2. Auditoría de GlitchType

  En  src-tauri/src/vostok_dsp/types.rs  (línea 43), el enum está definido así:

    pub enum GlitchType {
        Click, Pop, Dropout, Hum, Hiss, Slip, Distortion,
    }

  ¿Existe  GlitchType::Clipping ? NO. El sistema Rust ignora por completo la palabra "Clipping" y clasifica este fenómeno bajo el paraguas
  técnico de  Distortion .

  ### 3. Auditoría de Serialización

  El enum  GlitchType  utiliza la macro  #[serde(rename_all = "lowercase")] .
  El flujo de serialización exacto es:

  • Valor Rust:  GlitchType::Distortion
  • JSON a través de Tauri IPC:  "distortion"
  • Valor recibido por Frontend React:  "distortion"

  ### 4. Auditoría del Frontend

  En el frontend React sí existe soporte para renderizar y reparar  "distortion"  (incluso la UI etiqueta el botón como  "CLIP"  y le da color
  rojo). Sin embargo, encontré la Causa Raíz de la pérdida de eventos en  src/hooks/useGlitchManager.js  (línea 89):

      const [scanParams, setScanParams] = useState({
        clicks: true,
        hum: true,
        hiss: false,
        dropouts: true,
        distortion: false,  // <---- ¡DESCARTADO SILENCIOSAMENTE DESDE EL INICIO!
        sensitivity: 0.0,
        audio_mode: 'music',
      });

  Al correr el benchmark manualmente a través de la UI (como documentaste en P1.5), si no habilitaste la casilla explícita de "CLIP" (que viene
  apagada por defecto), Tauri recibe  params.distortion = false  y el backend Rust devuelve un vector vacío  Vec::new()  sin siquiera ejecutar
  detectar_clipping() .

  Por otro lado, al exportar el reporte en  VostokRestoration.jsx , el tipo  "distortion"  se transforma en mayúsculas ( "DISTORTION" ) y se
  escribe como evento puntual (sin  -> ), es decir:
   [01] PENDIENTE | 00:34.539 | DISTORTION | Canal: 0 ...

  ### 5. Auditoría del Benchmark

  El script evaluador ( tools/evaluar_vostok_v2.py ) tiene un parche para manejar esta discrepancia. En la función  canonical_type :

        elif "clipping" in t_str or "distortion" in t_str:
            return "Clipping"

  El script lee  "DISTORTION" , lo traduce correctamente a  "Clipping" .
  Luego, comprueba si es continuo:

    def is_continuous_type(c_type):
        return c_type in ["Hum", "Hiss", "Dropout"] # Clipping no está aquí

  Al ser considerado evento puntual, el script busca que el inicio del GT (34.532s) coincida con el inicio del reporte de Vostok (ej. 34.539s)
  con una tolerancia de  50ms . La distancia es de  7ms , por lo que haría MATCH perfectamente si el reporte TXT contuviera la anomalía.

  ### 6. Auditoría End-to-End (Tabla de Trazabilidad)

   ETAPA                                                                 | VALOR DE TRAZABILIDAD
  -----------------------------------------------------------------------|-----------------------------------------------------------------------
   Ground Truth (CSV)                                                    |  "clipping"
   Detector DSP (Rust)                                                   |  GlitchType::Distortion
   Serialización JSON                                                    |  "distortion"
   Filtro Frontend (useGlitchManager)                                    | FALSE (Apagado por defecto)
   Reporte TXT                                                           |  "DISTORTION"
   Benchmark Matcher                                                     |  "Clipping" (Vía canonical_type)

  ### 7. Diagnóstico Arquitectónico

  La HIPÓTESIS C es la principal responsable del fallo en tu banco de pruebas: El frontend (a nivel de estado de escaneo inicial) descarta el
  evento porque el detector está apagado por defecto ( distortion: false ). Dado que durante el benchmark solo ajustaste "modo Voz y sensibilidad
  al 0%", el detector de clipeo nunca se encendió.

  La HIPÓTESIS E (Inconsistencia de nomenclatura) es real ( Clipping  vs  Distortion ), pero el script  evaluar_vostok_v2.py  ya estaba diseñado
  para mitigarla mágicamente, por lo cual no fue la causante de los  FN = 2  en el benchmark final.

  ### 💡 Recomendación Estratégica para P1.7D

  1. Frontend: Cambiar el estado inicial en  useGlitchManager.js  para que  distortion: true  por defecto, o asegurarse de habilitarlo
  manualmente en la UI antes de exportar el reporte para el benchmark.
  2. Benchmark: Una vez que el TXT contenga los eventos de  DISTORTION , el recall de Clipping subirá, pero podríamos enfrentarnos a una pequeña
  fragmentación de eventos (un clipeo sostenido generando múltiples "flat-tops" consolidados cada 50ms). Si esto ocurre, solo requeriremos
  ajustar el orquestador en Rust o el script evaluador.
